# B09 — Skills, memoria y subagentes útiles

**Objetivo:** Ampliar capacidades después de tener un recorrido y una persistencia fiables.

**Dependencias de entrada:** B03, B05. Comprobar sus handoffs y el código.

## Contexto para el agente

Ya existe un agente principal y una skill. Mantener iguales políticas MCP, identidad e idempotencia. Memoria no es autorización y una skill nueva no modifica permisos.

Leer siempre `docs/PROJECT_CONTEXT.md` y `docs/CONTRACTS.md`. Las rutas de esta ficha son propuestas del repositorio; B00 las establece.

**Zona de trabajo:** packages/agents/, skills/, memoria y evals/agent_variants/.

**Fuera de alcance:** Autopromoción de skills, subagentes con UAMIs ficticiamente aisladas y registry dinámico general.

## B09.1 — Publicar skills por responsabilidad

**Modo:** LOCAL + LLM. **Depende de:** B03.4, B05.4.

**Implementar:** Separar comparación técnica, condiciones comerciales y preparación de solicitud en SKILL.md con referencias pequeñas. Publicarlas de solo lectura y registrar hashes/versiones. No cargar todas las instrucciones completas de golpe.

**Entregable:** Skills v1 y tests de selección/carga.

**Aceptación:** Cada escenario activa procedimientos pertinentes; una instrucción dentro de una oferta no modifica la skill ni los permisos.

**Entrega al siguiente agente:** `docs/handoffs/B09.1.md`, usando la plantilla común.

## B09.2 — Introducir dos subagentes

**Modo:** LOCAL + LLM. **Depende de:** B09.1.

**Implementar:** Añadir analista de ofertas y redactor con herramientas y contexto mínimos. El principal coordina y sintetiza; no delegar por delegar. Limitar profundidad/concurrencia y medir llamadas/coste respecto al agente único.

**Entregable:** Definiciones de subagentes y comparación con baseline.

**Aceptación:** Las evidencias llegan al principal y los especialistas no publican/aprueban fuera de alcance. Se documenta si la delegación mejora o empeora la tarea.

**Entrega al siguiente agente:** `docs/handoffs/B09.2.md`, usando la plantilla común.

## B09.3 — Gestionar memoria explícita

**Modo:** LOCAL. **Depende de:** B09.2.

**Implementar:** Persistir preferencias consentidas del usuario y conocimiento con procedencia/fecha. Aplicar namespace y operaciones de ver/editar/borrar. No convertir automáticamente una decisión puntual en regla global.

**Entregable:** Memoria de preferencias y políticas de escritura/retención.

**Aceptación:** Una preferencia aparece en otro hilo del mismo ámbito y no en el de otro usuario. Borrar memoria impide su uso posterior.

**Entrega al siguiente agente:** `docs/handoffs/B09.3.md`, usando la plantilla común.

## B09.4 — Proponer cambios de skill sin publicarlos

**Modo:** LOCAL + LLM. **Depende de:** B09.3.

**Implementar:** A partir de feedback, generar candidato de SKILL.md y diff con motivación, casos afectados y versión base. Guardarlo separado; no permitir editar el bundle activo. Preparar contrato de promoción que consumirá B10.

**Entregable:** Candidatos versionados y revisión humana.

**Aceptación:** El runtime sigue usando la versión aprobada. Cambiar una candidata no altera ejecuciones pendientes ni políticas MCP.

**Entrega al siguiente agente:** `docs/handoffs/B09.4.md`, usando la plantilla común.

## Puerta de salida del bloque

Dos especialistas aportan resultados verificables y la memoria aislada ayuda a una nueva tarea sin contaminar otros proyectos.

Revisar las cuatro entregas, integración y contratos modificados. Una dependencia externa pendiente se informa como tal; no se sustituye por un mock para declarar este bloque completo.
